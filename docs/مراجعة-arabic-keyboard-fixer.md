## 1. نظرة عامة سريعة

تطبيق ويب من طرف العميل (client-side) بحت يصحّح النص المكتوب بتخطيط لوحة مفاتيح خاطئ بين العربية والإنجليزية: تكتب `g]d la;gm` فيقترح عليك `لدي مشكلة`. يكتشف الاتجاه تلقائيًا، ويعرض اقتراحات مرتّبة بـ«درجة ثقة»، ويحفظ سجلًا محليًا لآخر 20 تصحيحًا.

البنية بسيطة ومسطّحة: `index.html` للهيكل، `css/styles.css` للتنسيق، `js/app.js` لكل المنطق، `locales/*.json` للنصوص، `service-worker.js` للعمل دون اتصال.

**التقنيات:** JavaScript خام (ES2020، بلا وحدات/modules)، CSS Variables، PWA (manifest + service worker)، i18n يدوي عبر `fetch` لملفات JSON. **صفر تبعيات npm، صفر خطوات بناء (build)** — قرار معماري ممتاز ومناسب تمامًا للمشكلة.

## 2. المراجعة التقنية والهندسية (45%)

### 2.1 البنية المعمارية وفصل المسؤوليات — **5/10**

`js/app.js` ملف واحد بـ 581 سطرًا يجمع سبع مسؤوليات مختلفة: جداول التخطيط، منطق التحويل الصافي، ربط DOM، طبقة i18n، التخزين المحلي، مستمعو الأحداث، وتسجيل service worker. المشكلة ليست الطول، بل أن **المنطق الصافي مربوط بالـ DOM على مستوى الوحدة**:

```js
const textInput = document.getElementById('textInput');
const suggestionsContainer = document.getElementById('suggestionsContainer');
```

هذي تُنفَّذ لحظة تحميل الملف، فيستحيل استيراد `convertToArabic`/`detectAndFix` في أي بيئة بلا DOM. الدليل القاطع على الضرر: ملف الاختبار اضطر يقصّ الملف نصيًا ويشغّله بـ `eval` (راجع 2.6).

**الحل:** استخرج `js/converter.js` كـ ES module يُصدّر `qwertyToArabic101/102`، `convertToArabic`، `convertToEnglish`، `detectAndFix`، `scoreArabicness` — بلا أي لمسة DOM. ثم `<script type="module" src="js/app.js">` مع `import`. التكلفة: ملف واحد إضافي. المكسب: اختبار حقيقي بالاستيراد، وحدّ واضح بين «المحرّك» و«الواجهة».

### 2.3 التكرار (DRY) و Code Smells — **6/10**

- **النص الافتراضي مكرر ثلاث مرات:** «مصحح لوحة المفاتيح العربية» موجود في `index.html` (نص ثابت)، وفي `locales/ar.json`، وكـ fallback في `t()`. أي تعديل يحتاج ثلاث لمسات، وتناقضها لا يكسر شيئًا فيمرّ صامتًا.

- **`charCountSpan.textContent` يُضبط في أربعة مواضع:** داخل `applySuggestion`، `buildHistoryItem.load`، `detectInput`، ومستمع `input`. الأسوأ أن `applySuggestion` يضبطه ثم يستدعي `detectInput()` الذي يضبطه مرة ثانية:
  ```js
  charCountSpan.textContent = fixed.text.length;
  detectInput();   // يضبط نفس القيمة مرة أخرى
  ```
  **الحل:** دالة واحدة `syncInputState()` تُستدعى بعد كل تغيير برمجي للقيمة.

- **`applySuggestion(index)` يعيد الحساب بدل استخدام المعروض:**
  ```js
  function applySuggestion(index) {
      const text = textInput.value;
      const suggestions = detectAndFix(text);   // إعادة حساب
      if (suggestions && suggestions[index]) { … }
  ```
  الاقتراحات المعروضة نُتجت من `detectInput` المؤجّل بـ 120ms. لو غيّر المستخدم النص ثم ضغط «تطبيق» خلال النافذة، الفهرس `index` يشير لعنصر مختلف عمّا رآه. **الحل:** خزّن آخر قائمة معروضة في `let currentSuggestions` ومرّر الكائن نفسه لا الفهرس — مصدر حقيقة واحد.

- **`el()` تتعامل مع `onClick` مرتين:** فرع خاص `k === 'onClick'` ثم فرع عام `k.startsWith('on')` يغطيه أصلًا. الفرع الأول زائد.

### 2.4 معالجة الأخطاء والحالات الحدّية — **4/10** ⬅ أضعف نقطة، وهنا أخطاء وظيفية مؤكّدة

المعالجة الدفاعية للبنية التحتية ممتازة (`try/catch` حول `localStorage`، تحقق من شكل السجل عند التحميل، `try/catch` في `detectInput`). لكن **بيانات التحويل نفسها — وهي جوهر المنتج — فيها أخطاء أثبتّها بالتشغيل**:

#### (أ) 🔴 حرف «ظ» غير موجود في التطبيق إطلاقًا

في `js/app.js` ضمن `qwertyToArabic101`:
```js
'z': 'ئ', 'x': 'ء', 'c': 'ؤ', 'v': 'ر', 'b': 'لا', 'n': 'ى', 'm': 'ة', ',': 'و', '.': 'ز', '/': '؟',
```
مفتاح `/` في تخطيط Arabic 101 الحقيقي هو **ظ**، و«؟» هي طبقة Shift عليه (`Shift+/`). التطبيق وضع قيمة الطبقة المزاحة في الطبقة الأساسية، فأسقط حرفًا كاملًا من الأبجدية. لا يحتاج هذا مرجعًا خارجيًا للإثبات: **حرف أبجدي أساسي غير قابل للإنتاج، بينما علامة ترقيم تحتل مفتاحًا أساسيًا** — تناقض داخلي كافٍ.

التحقق العملي (تشغيل فعلي على دوال المشروع):
```
letters NOT producible by 101: ظ أ إ آ
convertToEnglish("ظ") = "ظ"          ← يبقى كما هو، لا يُحوَّل
```
**الأثر المضاعف:** `arabicChars` مبنية من قيم الخريطة، فـ «ظ» لا تُحسب حرفًا عربيًا في `scoreArabicness` ولا في قرار زر ⇄. أي نص فيه «ظ» (ظهر، نظام، محافظة، انتظار…) يُحتسب بدقة أقل من الحقيقة، وقد يقلب قرار الاتجاه في النصوص القصيرة.

**الحل:** `'/': 'ظ'`، وإضافة طبقة Shift كخريطة ثانية `qwertyShiftToArabic101` تحوي `؟` و`أ` (`Shift+h`) و`إ` (`Shift+y`) و`آ` (`Shift+n`) و`لأ`/`لإ`/`لآ` — الأربعة `ظ أ إ آ` كلها غير قابلة للإنتاج حاليًا.

#### (ب) 🔴 خريطة Arabic 102 معطوبة داخليًا — مُثبت بلا حاجة لمرجع

المراجعة السابقة (`docs/ENGINEERING_REVIEW.md` بند 3.2) صنّفت هذا «ثقة متوسطة، بحاجة مرجع رسمي». **لا حاجة لمرجع** — الخريطة تناقض نفسها:

```
102 duplicate outputs: [ 'و', 'ز' ]
in 101 not in 102: [ 'ث', 'ح' ]
```

في `qwertyToArabic102`:
```js
'a': 'ل', 's': 'م', 'd': 'ن', 'f': 'ت', 'g': 'ة', 'h': 'خ', 'j': 'ه', 'k': 'ع', 'l': 'ق', ';': 'ط', "'": 'و',
'z': 'ئ', 'x': 'ء', 'c': 'ؤ', 'v': 'ر', 'b': 'لا', 'n': 'ى', 'm': 'ز', ',': 'و', '.': 'ز', '/': '؟',
```
مفتاحان يُنتجان «و» (`'` و `,`)، ومفتاحان يُنتجان «ز» (`m` و `.`)، بينما **«ث» و«ح» لا يُنتجهما أي مفتاح**. لا يوجد تخطيط لوحة مفاتيح حقيقي على وجه الأرض يخصص مفتاحين لنفس الحرف ويترك حرفين بلا مفتاح. النمط واضح: صفّ الرموز `, . /` نُسخ حرفيًا من خريطة 101 دون تكييف.

النتيجة العملية: مخرجات 102 هراء مطلق:
```
"g]d la;gm"  →  101: لدي مشكلة    |    102: ةضن قلطةز
```
والتطبيق يعرض الهراء جنبًا إلى جنب مع الصحيح، وبـ«دقة كشف» متطابقة (راجع (د)).

**الحل الفوري:** أخفِ اقتراح 102 خلف علم (feature flag) معطّل حتى يُصحَّح من مرجع موثّق (MSKLC / وثيقة تخطيط Windows). عرض بيانات خاطئة بثقة أسوأ من عدم عرضها. **الحل الدائم:** اشتقاق الخريطتين من مصدر واحد + اختبار «كل حرف عربي له مفتاح واحد بالضبط، ولا مفتاحان لنفس الحرف».

#### (ج) 🟠 التحويل العكسي لـ «لا» مكسور

```js
const arabicToQwerty101 = {};
Object.entries(qwertyToArabic101).forEach(([key, value]) => {
    if (!(value in arabicToQwerty101)) arabicToQwerty101[value] = key;
});
```
هذا ينشئ مفتاحًا `'لا' → 'b'`، لكن `convertToEnglish` تبحث **حرفًا حرفًا**:
```js
for (const char of text) result += arabicToQwerty101[char] || char;
```
فلا يمكن أن تصادف «لا» كوحدة أبدًا. المفتاح ميت والنتيجة خاطئة:
```
convertToArabic("b")   = "لا"
convertToEnglish("لا") = "gh"     ← المتوقع "b"
round-trip "hgb"       → "hggh"   ← الرحلة ذهابًا وإيابًا تفسد النص
```
**الحل:** في `convertToEnglish` افحص المتتاليات متعددة الأحرف أولًا (أطول تطابق أولًا) قبل السقوط للحرف المفرد.

#### (د) 🟠 «درجة الثقة» رقم بلا معنى — والترتيب حسبها لا يفعل شيئًا

`scoreArabicness` تقيس «كم نسبة الأحرف عربية». لكن كلتا الخريطتين تحوّلان *كل* حرف إنجليزي إلى *حرف عربي ما*، فالنتيجة متطابقة دائمًا:
```
"g]d la;gm"     → 101: 89   |   102: 89
"hgsghl ug d;l" → 101: 85   |   102: 85
"carrot pizza"  → 101: 92   |   102: 92
```
`suggestions.sort((a,b) => b.confidence - a.confidence)` عملية فارغة — الترتيب دائمًا 101 ثم 102 بحكم ثبات الترتيب. وREADME يعد بـ«درجة ثقة مستقلة» لكل تخطيط، وهذا غير صحيح.

الأخطر أن الرقم يُعرض للمستخدم كـ «دقة الكشف: 92%» على ناتج **هراء**: الجملة الإنجليزية السليمة `carrot pizza` تُعطي «ؤشققخف حهئئش» بثقة 92%. المقياس يقيس «هل الأحرف عربية» لا «هل النص عربي معقول».

**الحل:** استبدل المقياس بتحقق لغوي فعلي — تكرار الثنائيات/الثلاثيات العربية (bigram/trigram frequency) أو قائمة كلمات وظيفية شائعة (في، من، على، هذا، الذي…). لو تعذّر، **احذف عرض النسبة تمامًا** بدل تقديم رقم مضلل، واكتفِ بترتيب الاقتراحات.

#### (هـ) 🟠 النص المختلط — وهو الحالة الأكثر واقعية — يُرجع صفر اقتراحات

```js
if (englishCount > arabicCount && englishCount > text.length * 0.5) { … }
if (arabicCount > englishCount && arabicCount > text.length * 0.5) { … }
```
شرط «الأغلبية المطلقة لأكثر من نصف النص كله» يعني أن أي فقرة عربية سليمة فيها كلمة واحدة مكتوبة بالخطأ لا تحقق أي فرع:
```
detectAndFix("رسالة: g]d")  →  []   (لا اقتراحات إطلاقًا)
```
وهذا بالضبط ما يحدث في الواقع: تكتب جملة، تنسى التبديل لكلمة أو كلمتين، تنتبه. التطبيق يصمت. وفي المقابل ينتج إيجابيات كاذبة على إنجليزية سليمة (`Hi! I am here...` → اقتراحان).

**الحل:** طبّق الكشف **على مستوى الكلمة** لا النص كله: قسّم على المسافات، حوّل الكلمات المشبوهة فقط، وأبرزها للمستخدم قبل التطبيق. هذا هو التحسين الأعلى أثرًا في المنتج كله.

#### (و) 🟡 فشل تحميل الترجمة صامت للمستخدم

```js
} catch (err) {
    console.warn('Locale load failed; keeping baseline HTML:', err);
}
```
عند فتح الملف عبر `file://` (وهو ما سيفعله كثيرون) يفشل `fetch`، فيبقى HTML الأساسي العربي ويصير زر «English» بلا فعل — بلا أي إشارة للمستخدم. الحل: عطّل زر اللغة بصريًا وأظهر toast «تبديل اللغة يتطلب تشغيل التطبيق عبر خادم HTTP».

### 2.5 الأداء واستهلاك الموارد — **7/10**

الأداء ممتاز عمليًا (خوارزميات O(n)، بلا تبعيات، debounce 120ms مناسب). ملاحظتان عند الحدّ الأقصى المسموح (50,000 حرف):

1. **عرض 100 ألف حرف في DOM لكل تحديث:** `buildSuggestionItem` تضع نص الاقتراح كاملًا في `.suggestion-content` — اقتراحان × 50k = 100k حرف يُعاد بناؤها كل 120ms أثناء الكتابة. لاحظ التناقض: السجل يقتطع عند 50 حرفًا (`item.fixed.substring(0, 50)`) بينما الاقتراح لا يقتطع أبدًا.
   **الحل:** اعرض معاينة مقتطعة (500 حرف) في `.suggestion-content`، والنص الكامل يبقى في الذاكرة للتطبيق/النسخ.

2. **`[...text]` يجسّد مصفوفة كاملة:** في `scoreArabicness` و`detectAndFix` وزر ⇄ — ثلاث مصفوفات بـ 50 ألف عنصر لكل تقييم. استبدلها بعدّاد في حلقة `for…of` واحدة.

### 2.6 الاختبارات — **4/10**

12 اختبارًا تمر (تحققت بالتشغيل)، بلا تبعيات، وتعمل في CI على كل push و PR. لكن:

**(أ) الحزام هشّ بشكل خطير:**
```js
const startFns = findLine('function convertToArabic');

**(ب) الأخطر — التغطية تفوّت كل عيب حقيقي:** لا يوجد **ولا اختبار واحد** يمسّ `qwertyToArabic102` رغم أنها أهم بيانات في المشروع، ولا اختبار للرحلة ذهابًا وإيابًا (round-trip)، ولا اختبار لاكتمال الأبجدية. ثلاثة اختبارات بسيطة كانت ستكشف كل عيوب 2.4 فورًا:

record('لا مفتاحان يُنتجان نفس الحرف في 102', () => {

    return new Set(v).size === v.length;

record('الرحلة ذهابًا وإيابًا تحافظ على النص', () => {

    return convertToEnglish(convertToArabic(src, qwertyToArabic101)) === src;

```

**(ج) صفر تغطية لطبقة الواجهة:** لا شيء يغطي `detectInput`، `applySuggestion`، السجل، أو i18n.

**قراءة الدرجة بصراحة:** الهندسة المحيطة بالمنتج ناضجة بدرجة تفوق حجم المشروع بكثير — CSP، PWA، i18n، a11y حقيقية، CI، صفر تبعيات، توثيق منظّم. لكن **البيانات في القلب خاطئة**: حرف عربي كامل مفقود، وخريطة تخطيط ثانية معطوبة داخليًا، ومقياس ثقة لا يقيس شيئًا. الدرجة تعكس هذي المفارقة تحديدًا: مشروع بواجهة 8/10 على محرّك 4/10. والجانب المشرق أن الأخطاء الأربعة الأولى في خطة الإصلاح **بيانات لا معمارية** — إصلاحها ساعات لا أسابيع، وسترفع الدرجة إلى نطاق 8 مباشرة.

**ملاحظة على المراجعة السابقة:** `docs/ENGINEERING_REVIEW.md` أعطى 8/10. الفارق ليس تشدّدًا: تلك المراجعة قيّمت بنية الكود، وهذه شغّلت الكود. عيوب «ظ» و«لا» وتطابق درجات الثقة والنص المختلط لا تظهر بالقراءة، فقط بالتنفيذ. وللإنصاف، أغلب ما رصدته تلك المراجعة **أُصلح فعلًا** (معالج اللصق المدمّر، CSP، `package.json`، الكود الميت، وقت السجل، CONTRIBUTING، ضجيج aria-live) — وهذا يُحسب للمشروع.
